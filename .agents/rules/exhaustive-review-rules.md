# Exhaustive Review & Verification Rules (網羅的レビュー・検証規約)

**Activation:** This rule is **ALWAYS ON** for all files (`**/*`).

コードレビュー（`/review` を含む）および修正後のセルフレビューを行う際は、複数回のやり直しを発生させず1回のレビューで問題点を取り切るため、以下の手順を厳守する。

## 1. レビュー対象スコープの厳格な限定（変更箇所と直接の依存先のみ）
ユーザーから「プロジェクト全体」「特定モジュール全体」といった明示的な範囲指定がない限り、レビュー対象は**現在の会話内で変更したファイル（または未コミットの `git diff`）および変更した関数・クラスの直接の呼び出し元・呼び出し先**のみに限定する。会話内で編集していない無関係な既存ファイルへ勝手にスコープを広げてはならない。対象範囲を固定することで、レビューのたびに未修正の別ファイルから新たな指摘が際限なく出てくる事態を防ぐ。

## 2. 実ファイルの必読（要約・記憶への依存禁止）
会話履歴の自動要約（コンパクション）後や修正ループの直後にレビューを行う際、要約テキストや過去の記憶だけを根拠に「問題なし」と判定してはならない。スコープ内の対象ファイルを必ず `read_file` で実際に読み込み、最新のコード全文を確認したうえで判定する。

## 3. 早期打ち切りの禁止とスコープ内の横串照合（1パス完走）
数件の指摘事項が見つかった時点で探索を打ち切ってはならない。対象スコープ内の全変更箇所を最後まで走査し、1回のパスで潜在的な不具合をすべて出し切る。変更箇所のなかで問題を1件発見した場合は、**今回の変更対象ファイル群の内部**で同じパターンの問題が他にないかをその場で横串照合し、1回のレビューでまとめて洗い出す。

1. **プロトコル境界・入力検証の照合:**
   - 変更したコマンドや API 経路に対して、交渉済み上限値（`MaxReadSize` / `MaxWriteSize` / `MaxTransactSize` 等）によるクランプ、パスや名前の正規化・空文字検証、未知の識別子や不正応答の拒否、および分割応答（マルチフラグメント等）の再結合処理が揃っているかを確認する。
2. **リソースライフサイクル・排他制御の照合:**
   - 変更した `AutoCloseable`・接続・ストリーム・UI 実装に対して、初期化途中の例外発生時におけるロールバック解放、クローズ状態（`isClosed`）の公開とクローズ後操作のガード、および画面・ウィンドウ破棄時の `CoroutineScope` キャンセルと `NonCancellable` クリーンアップが漏れていないかを確認する。
3. **複数箇所・複数プラットフォームを同時変更した場合の一貫性照合:**
   - 今回の会話で複数のクラスや複数のプラットフォーム（Android / iOS / Windows Native / JVM）を同時に変更している場合は、それらの変更箇所間でセッション管理、UI 状態キーの粒度、エラー復帰とリソース解放の挙動が統一されているかを確認する。
